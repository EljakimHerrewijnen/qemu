# QEMU Hedgehog Development Guide

All paths in this guide are relative to the repository root. This file is the
authoritative implementation guide for Hedgehog work.

## Using The Custom Instructions

Use the repository guidance in this order:

1. Read `AGENTS.md` for repository-wide operating and publication rules.
2. Read this file for implementation boundaries and validation requirements.
3. Read only the matching guide under `.github/agents/` for the current task.
4. Read `HEDGEHOG_RESEARCH.SKILL.md` before cross-layer research or design.

The files under `.github/agents/` are task guides. A client may discover them
automatically, but do not assume that agent activation or slash commands are
available. Apply their checklists directly when those features are absent.

Local plans and notes under ignored directories may help during development,
but they are optional and must not be prerequisites for understanding a public
change. Put durable behavior and contributor guidance in tracked documentation.

Do not stage, commit, fetch, rebase, tag, publish, or push unless the user has
explicitly requested that operation. Read-only Git inspection is allowed.

## Quick Context

Hedgehog exposes selected QEMU CPU, memory, hook, and board services through the
Python package in `python/qemu/hedgehog/`.

Primary implementation areas:

- Native backend: `accel/hedgehog/hedgehog.c`
- Public C ABI: `include/system/hedgehog-backend.h`
- TCG hook registry: `accel/tcg/hedgehog-exec-hooks.c`
- TCG hook call sites: `accel/tcg/cpu-exec.c`, `accel/tcg/cputlb.c`
- Python API and ctypes bridge: `python/qemu/hedgehog/api.py`,
  `python/qemu/hedgehog/backend.py`
- Tests: `python/tests/test_hedgehog_api.py`,
  `tests/unit/test-hedgehog-backend-api.c`

## Execution Models

- Standalone mode creates a CPU and caller-managed RAM/MMIO without realizing a
  complete QEMU board.
- Machine mode realizes a QEMU machine and its device model. Configuration that
  must exist before device realization belongs in QEMU properties and generic
  Hedgehog property bindings.
- Do not expose a private machine profile as a Hedgehog API. Keep reusable
  architecture behavior in QEMU and target-specific policy in an untracked
  harness.

## Implementation Patterns

- Preserve unrelated dirty work. Run `git status --short` and inspect diffs for
  files you need to edit.
- Keep QEMU integration points narrow and conditional. Avoid broad TCG or board
  refactors unless the feature requires them.
- When changing the native ABI, update the C declaration, ctypes signatures,
  Python protocol/wrapper, fake backend tests, C ABI test, and docs together.
- Treat standalone and board-backed machine modes as separate execution models.
  A helper that is valid for standalone CPU state may be invalid after a real
  board has realized its CPUs.
- Do not hide native behavior behind Python-only mocks. Include a native build or
  smoke test when runtime CPU/QEMU behavior changes.
- Classify every change as QEMU-owned, Hedgehog-owned, or local tooling. A file
  in the QEMU source tree is not automatically suitable for upstream QEMU when
  it calls Hedgehog-specific interfaces.
- Put reusable processor behavior in the appropriate QEMU target or machine
  model. Keep embedding policy, callback transport, and rare-instruction
  fallback behavior in Hedgehog.

## Publication Safety And Target Neutrality

Tracked code, tests, documentation, commit messages, and release artifacts must
not identify a private analysis target. Do not add:

- vendor, product, board, SoC, firmware, boot-stage, or project code names;
- target-derived register lists, reset values, memory maps, keys, addresses, or
  binary fragments unless they are public architectural data required by QEMU;
- private artifact paths, workstation paths, usernames, internal URLs, tokens,
  credentials, dumps, generated native libraries, or local analysis notes.

Use architectural terminology, generic QEMU machine properties, synthetic
instruction encodings, and minimal target-neutral fixtures. If local target
material is needed for investigation, put it under the repository-local
`.hedgehog-local/` directory and first verify the exact path with
`git check-ignore -v <path>`. Do not add broad ignore rules such as `*.bin`,
`*.elf`, or `*.img`: QEMU can legitimately track fixtures with those suffixes,
and an ignored file can still be force-added.

Before any proposed commit or push:

1. Run `git status --short` and identify tracked, staged, untracked, and ignored
   artifacts separately.
2. Stage explicit paths only; do not use `git add -A` for mixed worktrees.
3. Review `git diff --cached --name-status`, `git diff --cached`, and
   `git diff --cached --check`.
4. Search the staged diff for known private identifiers and credential patterns.
   Report matching file names without copying possible secret values into logs.
5. Verify generated libraries, firmware, dumps, plans, and local profiles are
   absent from the staged set.
6. Re-run focused tests from a cleanly identified build before publication.
7. For distributable native artifacts, compile with
   `-ffile-prefix-map=<checkout>=.` and scan the finished artifact for absolute
   checkout paths. Ignoring a local wheel protects Git; it does not protect a
   separately uploaded release artifact.

An empty staged diff does not prove the worktree is safe to commit later; audit
untracked files as well. Conversely, if `HEAD` has no commits ahead of its
upstream, an ordinary push transmits no current worktree changes.

## Common Tasks

### Add A New Hook Type

1. Define a target-neutral C event and callback contract.
2. Add the hook registry and the narrowest viable QEMU call site.
3. Add architecture classification behind a target-conditioned adapter when
   target-private state is required.
4. Extend the ctypes bridge, `BackendProtocol`, and public Python API.
5. Test callback registration, pass-through, handling, errors, and native guest
   continuation.
6. Update API and architecture documentation together.

### Add A Python-Facing Backend Function

1. Add the declaration to `include/system/hedgehog-backend.h`.
2. Implement the function in `accel/hedgehog/hedgehog.c`.
3. Add ctypes argtypes/restype in `python/qemu/hedgehog/backend.py`.
4. Extend `BackendProtocol` and `NativeBackend`.
5. Expose a public helper in `python/qemu/hedgehog/api.py` only when useful.
6. Extend `python/tests/test_hedgehog_api.py`.
7. Add ABI coverage in `tests/unit/test-hedgehog-backend-api.c`.
8. Update `python/qemu/hedgehog/docs.md` and any active local plan.

### Validate Changes

Use the checkout-local wrapper first when it is present:

```bash
llm_tools/llm_scripts/hedgehog_validate.sh
```

For focused runs:

```bash
git diff --check
PYTHONPATH=python python3 -m pytest python/tests/test_hedgehog_api.py
ninja -C build libqemu-hedgehog-backend.so
ninja -C build tests/unit/test-hedgehog-backend-api
./build/tests/unit/test-hedgehog-backend-api
```

## Upstream Management

Hedgehog touches upstream-sensitive QEMU areas: TCG execution, memory faults,
build files, and ARM board integration. Prefer small patch sets with clear
boundaries. For merge planning, use `.github/agents/upstream-sync.agent.md` and
record durable conflict-resolution guidance in tracked repository docs. Keep a
QEMU-upstreamable patch independent from Hedgehog symbols and submit it
separately from fork integration.

## Troubleshooting

- Backend library not found: set `QEMU_HEDGEHOG_BACKEND_LIBRARY` to the built
  `libqemu-hedgehog-backend.so`.
- Python imports stale code: run from the repository root with
  `PYTHONPATH=python`.
- Native backend reuse fails: create each real native backend in a fresh process.
- Machine-mode property/chardev failures usually mean bindings were applied
  after board realization.
